Straight answers first

What was I asked to do?
VLM-FO1 is built on top of the Qwen2.5-VL vision-language model. Your task is to make the codebase run on Qwen3.5 instead — Alibaba’s newer model family released in February 2026. “Architectural changes only” means: rewire the code so the new backbone fits, but do not train or fine-tune anything. The branch name of this task (qwen-to-35) confirms the target.
Is it already done?
No. I checked the git history: this fork is identical to the upstream project, and your working branch has zero code changes. What probably caused the confusion is that the project advertises itself as “plug-and-play with any VLM” — the architecture is deliberately modular, and the finished Qwen2.5-VL integration acts as a template you can copy. So the ground is prepared, but the Qwen3.5 swap itself has not been written.
Why is “no training” even possible?
Because the assignment is about code integration, not model quality. You make the pipeline load Qwen3.5, run an image through it, and produce output without crashing. The learned glue layers (projectors) were trained against Qwen2.5-VL, so answer quality after the swap will be poor until someone retrains them — that is expected and explicitly out of your scope. See Part IV.
Where do I start?
Read Part I to understand the machine you are modifying, skim Part II for what is different about Qwen3.5, then follow the numbered steps in Part III. Throughout this page, teal tags mark existing files and amber tags mark things you must create or change.

Part I

The big idea

Large vision-language models (VLMs) like Qwen2.5-VL are excellent at reasoning about an image (“what is happening here?”) but mediocre at precisely locating things in it. Asking a VLM to output pixel coordinates for “every orange in this photo” gives you fuzzy, unreliable boxes.

VLM-FO1 (paper: arXiv 2509.25916) sidesteps the problem with one elegant trick: it never asks the model to produce coordinates. Instead:

  1. An external detector (UPN or SAM3) — or the user — supplies candidate bounding boxes.
  2. Each box is encoded into a single region token: a vector that describes what is inside that box, injected into the prompt as <region0>, <region1>, …
  3. The language model answers by naming region indexes: <ground>orange</ground><objects><region0><region3></objects>.
  4. A small parser maps those indexes back to the original boxes and draws them.

Detection becomes a multiple-choice problem instead of a regression problem — which language models are very good at. The quality of a region token is what makes this work, so the project builds it from two vision encoders at once (the “Hybrid Fine-grained Region Encoder”, HFRE): the VLM’s own vision tower contributes semantic meaning, and a second detection-oriented backbone (DaViT) contributes sharp spatial detail.

Everything is bolted around a frozen, pre-trained Qwen2.5-VL — its weights and abilities are preserved. That is the modularity you will exploit: the backbone is a replaceable part.

One request, end to end

Follow a single call to inference.py through the code:

  1. Message assembly. You pass chat messages plus a bbox_list. prepare_inputs() in vlm_fo1/mm_utils.py:532 builds a ChatML prompt. For every image it inserts <|vision_start|><image><|vision_end|>, and for every box it appends <region0><regionfeat><region1><regionfeat>…. The literal text <region0> stays as readable text (so the model can echo it back), while each <regionfeat> becomes placeholder id −300 and each <image> becomes −200 (vlm_fo1/constants.py).
  2. Image preprocessing. The same image is prepared twice: once by the Qwen image processor (dynamic resolution, giving pixel_values + image_grid_thw) and once squashed to 768×768 for DaViT. Boxes are rescaled to match (vlm_fo1/mm_utils.py:597-623).
  3. Main tower. encode_images() (…/language_model/omchat_qwen2_5_vl.py:44) runs the Qwen2.5 ViT. A monkey patch (…/multimodal_encoder/qwen2_5_vl_encoder.py:86-171) also captures hidden states at the ViT’s four full-attention layers — a free multi-scale feature pyramid.
  4. Region tokens. encode_regions() (omchat_qwen2_5_vl.py:75) runs DaViT, then the HFRE module (…/hybrid_finegrained_region_encoder.py) roi_aligns every box against both feature sets, pools, adds a sine position embedding of the box geometry, and concatenates → one vector per box → mm_projector_aux lifts it to LLM width.
  5. Splice. prepare_inputs_labels_for_qwen2_5_vl_multimodal() (omchat_qwen2_5_vl.py:135) walks the token sequence and replaces every −200 slot with the image token embeddings and every −300 slot with its region token. It then computes Qwen’s multimodal rotary position ids via get_rope_index().
  6. Generate & parse. Standard HuggingFace generate(). The output string is parsed by extract_predictions_to_bboxes() (mm_utils.py:316) with a regex over <ground>…<objects>…, mapping indexes back to your original boxes.

Component deep-dives

The model classes — omchat_qwen2_5_vl.py

This 577-line file is the template you will copy. It defines three classes that sandwich FO1’s additions into HuggingFace’s Qwen2.5-VL:

OmChatQwen25VLConfig(Qwen2_5_VLConfig)          # adds model_type "omchat_qwen2_5_vl"
OmChatQwen25VLModel(OmChatMetaModel, Qwen2_5_VLModel)   # decoder + FO1 modules
OmChatQwen25VLForCausalLM(Qwen2_5_VLForConditionalGeneration, OmChatMetaForCausalLM)

Multiple inheritance does the trick: OmChatMetaModel (from omchat_arch.py) runs first and attaches vision_tower, vision_tower_aux, mm_projector, mm_projector_aux and object_vp_extractor (the HFRE) as submodules — so their weights live inside the same checkpoint and load automatically with from_pretrained(). The last two lines register the custom model_type with transformers’ Auto classes.

Key methods: encode_images() (main tower + projector), encode_regions() (aux tower + HFRE + aux projector), prepare_inputs_labels_for_qwen2_5_vl_multimodal() (the splice — the longest and most important method), and a forward() that builds embeddings itself and then defers to the parent Qwen forward.

The config contract — omchat_arch.py + checkpoint config.json

Nothing is hard-wired to a model size; everything is read from the checkpoint’s config.json. The keys that matter (and who reads them):

Main tower + monkey patch — qwen2_5_vl_encoder.py

Qwen2_5_VlVisionTower wraps the ViT that ships inside Qwen2.5-VL. The interesting part is the monkey patch: Qwen2.5’s ViT uses windowed attention in most layers and full attention in only four (fullatt_block_indexes). The patch replaces the ViT’s forward() with a copy that (a) stores the hidden states at those four layers and (b) un-shuffles the window ordering back to a raster grid, yielding four feature maps of shape [1, C, H, W] per image — the “vision-tower pyramid” the HFRE consumes. This is the most Qwen2.5-specific code in the project, and its complexity exists only because of window attention. Remember that for later: Qwen3.5’s ViT has no windows, so the replacement is simpler.

Aux tower, HFRE, projectors

DaViT (davit_aux_encoder.py) is a detection-grade backbone producing a classic 4-stage pyramid with channels [256, 512, 1024, 2048] from a fixed 768×768 input. It is loaded from the FO1 checkpoint and knows nothing about Qwen — completely untouched by the swap.

HFRE (hybrid_finegrained_region_encoder.py) is where region tokens are born: roi_align over the DaViT pyramid (concatenated channels) and over the ViT pyramid (boxes rescaled to each tower’s coordinate space), mean-pool each ROI, add sinusoidal embeddings of the box position/size, combine (concat by default), LayerNorm. Pure geometry + torch ops, no Qwen dependency — untouched.

Projectors (multimodal_projector/builder.py) are small MLPs: mm_projector maps main-tower features → LLM width; mm_projector_aux maps HFRE output → LLM width. Their in/out sizes come from config, so the code never changes — but their trained weights are married to Qwen2.5’s embedding space. That is the load-bearing caveat of a no-training swap.

Detectors, demos, evaluation

detect_tools/upn/ is a vendored copy of UPN from ChatRex — an open-vocabulary proposal generator with deformable-attention CUDA ops (built separately via pip install -v -e . inside detect_tools/upn/ops). scripts/inference_with_upn.py and …_with_sam3.py chain a detector in front of FO1; demo/ holds three Gradio apps (plain, +SAM3, +SAM3 video tracking). All of them only talk to FO1 through load_pretrained_model() and prepare_inputs(), so they inherit the swap for free once loading works.

Part II

What Qwen3.5 actually is

Qwen3.5 (released 16 Feb 2026) is not “Qwen2.5 but newer” — it is a different animal in three ways that matter to this codebase:

  • Natively multimodal. There is no separate “-VL” variant. Every Qwen3.5 checkpoint (Qwen/Qwen3.5-0.8B, -4B, -9B, -27B, -397B-A17B) is trained from scratch on interleaved text, image and video, with the vision encoder inherited from Qwen3-VL.
  • Hybrid attention decoder. The text stack interleaves Gated DeltaNet (linear-attention) layers with gated full-attention layers at roughly 3:1 (the Qwen3-Next design), and the larger models are sparse MoE. From the outside it is still a causal LM with a KV-ish cache, so generate() works normally — but it is a different implementation living in transformers ≥ v5.2 as the qwen3_5 model family.
  • Cleaner vision tower. Qwen3_5VisionModel uses full attention in every block (no windows, no fullatt_block_indexes, no window-index shuffling), learned position embeddings with interpolation instead of 2D RoPE, and a single patch merger. Its forward returns both the pre-merge patch features (last_hidden_state) and the merged tokens (pooler_output).

For your migration, the class inventory in transformers v5 is:

Qwen3_5Config, Qwen3_5TextConfig, Qwen3_5VisionConfig
Qwen3_5VisionModel            # the ViT
Qwen3_5TextModel              # the decoder stack (embed_tokens lives here)
Qwen3_5Model                  # visual + text, wired together
Qwen3_5ForCausalLM            # text-only LM head
Qwen3_5ForConditionalGeneration   # the full multimodal model
Qwen3_5CausalLMOutputWithPast # output type (carries rope_deltas)

Part III

What changes, what stays

Step-by-step migration plan

The strategy is parallel, not destructive: keep every Qwen2.5 file working, add Qwen3.5 files alongside, and let the existing name-based dispatch pick between them. Class names below were verified against transformers main (Aug 2026); pin your exact version first and re-check signatures against your installed copy — v5 is still moving.

STEP 0

Environment — requirements.txt

Qwen3.5 needs transformers ≥ v5.2; the repo pins 4.50.1. This is the one genuinely disruptive change: the vendored Qwen2.5 modeling code imports transformers internals that moved in v5, so after upgrading, test whether the old path still imports. If it breaks and you must keep both backbones runnable, use two virtualenvs (one per backbone); if only Qwen3.5 matters for your deliverable, let the old path break gracefully behind its dispatch branch.

STEP 1

New tower wrapper — vlm_fo1/model/multimodal_encoder/qwen3_5_encoder.py

Copy qwen2_5_vl_encoder.py and simplify. Because Qwen3.5’s ViT is full-attention with no window shuffle, you do not port the monkey patch — plain forward hooks on four evenly spaced blocks give the same multi-level pyramid, already in raster order:

from transformers.models.qwen3_5.modeling_qwen3_5 import Qwen3_5VisionModel
from transformers import AutoImageProcessor

class Qwen3_5VisionTower(nn.Module):
    def __init__(self, image_tower, args, delay_load=False,
                 min_pixels=56*56, max_pixels=2048*2048):
        super().__init__()
        self.is_loaded = False
        self.image_tower_name = image_tower
        self.use_vision_tower_region_feature = getattr(
            args, "mm_use_vision_tower_region_feature", False)
        self.min_pixels, self.max_pixels = min_pixels, max_pixels
        self.cfg_only = args.vision_config
        self.load_model(model_path=args.name_or_path)

    def load_model(self, model_path=None, image_size=336, is_train=True):
        self.image_tower = Qwen3_5VisionModel._from_config(
            self.cfg_only, torch_dtype=torch.bfloat16)   # weights arrive via from_pretrained
        self.image_processor = AutoImageProcessor.from_pretrained(
            model_path or self.image_tower_name,
            min_pixels=self.min_pixels, max_pixels=self.max_pixels)
        if self.use_vision_tower_region_feature:
            self._install_level_hooks()                  # replaces the 2.5 monkey patch
        self.is_loaded = True

    def _install_level_hooks(self):
        depth = len(self.image_tower.blocks)
        self.level_ids = {depth//4 - 1, depth//2 - 1, 3*depth//4 - 1, depth - 1}
        self._levels = []
        for i, blk in enumerate(self.image_tower.blocks):
            if i in self.level_ids:
                blk.register_forward_hook(
                    lambda mod, inp, out: self._levels.append(
                        out[0] if isinstance(out, tuple) else out))

    def forward(self, images, image_grid_thws=[]):
        feats, grids, multi = [], [], []
        for i, image in enumerate(images):
            if not image_grid_thws:
                image, grid = self.convert_image_format(image)   # same as 2.5 wrapper
            else:
                grid = image_grid_thws[i]
            self._levels = [] if self.use_vision_tower_region_feature else None
            out = self.image_tower(image.to(self.device, self.dtype),
                                   grid_thw=grid.to(self.device))
            feats.append(out.pooler_output.unsqueeze(0).to(self.dtype))  # merged tokens
            grids.append(grid)
            if self.use_vision_tower_region_feature:
                multi.append(self._reshape_levels(grid))  # seq → [1, C, H, W] per level
        return feats, grids, multi

    @property
    def hidden_size(self):        # feeds mm_hidden_size consumers
        return self.config.out_hidden_size

_reshape_levels is the only real work: each hooked tensor is [seq, C] in raster order, so t.reshape(H, W, C).permute(2, 0, 1).unsqueeze(0) with H, W = grid_thw[0][1:] — no argsort(window_index) gymnastics. Keep the returned structure identical to the 2.5 wrapper (list of 4 maps per image) so the HFRE code path does not change.

  • The v5 signature needs token types. Where the 2.5 file builds rope_index_kwargs (old line ≈ 449), add: 
    mm_token_type_ids = (new_input_ids == self.config.image_token_id).int()
position_ids, rope_deltas = self.get_rope_index(
    new_input_ids, mm_token_type_ids,

STEP 4

Dimension formula — omchat_arch.py:26

The HFRE is told how wide the main-tower pyramid is: hidden_size * 4 (four gathered layers × ViT width). That formula still holds if you hook four levels in Step 1 — just be aware Qwen3.5’s ViT hidden_size differs from Qwen2.5’s 1280, and the value flows from vision_config automatically. If you hook a different number of levels, change the multiplier here to match.

STEP 5

Tokens and prompt format — constants.py, mm_utils.py

make_message_context() hard-codes ChatML ids 151644/151645 (mm_utils.py:483-484, 573, 581) and constants.py pins <|image_pad|> = 151655. Qwen3.5 keeps a ChatML-style template but its vocabulary is its own — never trust inherited ids. Replace the literals with startup lookups:

IM_START_ID = tokenizer.convert_tokens_to_ids("<|im_start|>")
IM_END_ID   = tokenizer.convert_tokens_to_ids("<|im_end|>")
IMAGE_PAD_ID = model.config.image_token_id     # already config-driven at the splice

Verify with a five-line REPL session against the real Qwen3.5 tokenizer before wiring anything. The placeholder scheme (−200 / −300) is FO1-internal and needs no change. Also confirm AutoTokenizer.from_pretrained(path, use_fast=False) works for Qwen3.5 under v5 (model/builder.py:37) — if the slow tokenizer is unavailable, drop use_fast=False and re-test the allowed_special kwargs in make_message_context.

STEP 6

Assemble a runnable checkpoint — weight surgery, no training

There is no trained FO1-on-Qwen3.5 checkpoint, so build a composite folder that loads. One throwaway script:

# scratch/make_fo1_qwen35_checkpoint.py — run once on CPU
base = Qwen3_5ForConditionalGeneration.from_pretrained("Qwen/Qwen3.5-4B")
fo1  = load_safetensors_dir("resources/VLM-FO1_Qwen2.5-VL-3B-v01")

# 1. Qwen3.5 decoder → the FO1 prefix for the text stack

# 2. Qwen3.5 ViT → the tower wrapper's prefix
sd.update(remap(base.model.visual.state_dict(), to="model.vision_tower.image_tower."))
# 3. FO1's own modules, carried over verbatim (Qwen-independent)
for k, v in fo1.items():
    if k.startswith(("model.vision_tower_aux.", "model.object_vp_extractor.")):
        sd[k] = v
    # projectors: copy ONLY if shapes match the new hidden sizes — else skip
    if k.startswith(("model.mm_projector.", "model.mm_projector_aux.")) \
       and shapes_match(k, v, new_config):
        sd[k] = v
save_safetensors(sd, "resources/VLM-FO1_Qwen3.5-4B/")

Then write the folder’s config.json: start from Qwen/Qwen3.5-4B’s config, set model_type: "omchat_qwen3_5", architectures: ["OmChatQwen35ForCausalLM"], and copy every mm_*, aux_image_* key from the FO1 checkpoint’s config, updating mm_hidden_size (= new ViT out_hidden_size) and leaving hidden_size to the Qwen3.5 base. Copy the Qwen3.5 tokenizer + preprocessor files in too. If projector shapes don’t match (they won’t: 2048-wide Qwen2.5-3B vs the 4B’s width), those layers initialize randomly — the pipeline still runs, which is exactly the deliverable. Exact parameter prefixes: print a few keys of the FO1 safetensors and of your new model’s state_dict() and align them — five minutes of inspection beats guessing.

  • python -c "from transformers.models.qwen3_5 import modeling_qwen3_5" — environment is really on v5 with the family present.

Part IV

Why “no fine-tuning” makes sense — and what to say about results

The pretrained FO1 checkpoint contains three kinds of weights: the Qwen2.5-VL backbone (frozen from Alibaba), FO1’s perception modules (DaViT, HFRE — largely Qwen-independent), and the projectors, which were trained specifically to translate visual features into Qwen2.5’s embedding space. Swap the backbone and that translation is addressed to a reader who no longer lives there: Qwen3.5’s embedding space has a different width and different geometry.

So the honest framing of your deliverable — and this is a normal, legitimate engineering milestone — is: the architectural integration. The pipeline loads Qwen3.5, images flow through both towers, region tokens are spliced, generation runs, output parses. Answer quality is expected to be degraded until someone reruns the paper’s two-stage alignment training, which is precisely the part you were told not to do. Say that sentence to whoever reviews your work and you will sound like you understood the assignment — because you did.

Glossary

VLMVision-language model — an LLM that also accepts images.
vision towerThe image-encoder half of a VLM (a Vision Transformer here).
region tokenOne embedding vector summarizing the content of one bounding box, injected into the prompt like a word.
HFREHybrid Fine-grained Region Encoder — FO1’s module that builds region tokens from two feature pyramids via roi_align.
roi_alignTorchvision op that crops a feature map to a box and resamples it to a fixed grid.
projectorSmall trained MLP translating encoder features into the LLM’s embedding width.
monkey patchReplacing a method on a class at runtime — here, the ViT forward, to expose internal features.
M-RoPEQwen’s multimodal rotary position encoding: separate position axes for time, height, width.
grid_thwPer-image (temporal, height, width) patch counts; drives token counts and positions.
UPN / SAM3External detectors used to propose candidate boxes for FO1 to reason over.
Gated DeltaNetLinear-attention layer type used in 3 of every 4 Qwen3.5 decoder layers.
MoEMixture-of-Experts — only a fraction of weights active per token (e.g. 397B-A17B = 17B active).
